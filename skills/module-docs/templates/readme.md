# Module docs

One living page per product module, read by the client and the developers
alike: what the module is, what is built now, what is coming next, what is
still open, and a dated history of how it got here - what changed, why, how it
was planned and what was decided.

Kept by the `module-docs` skill. Nobody writes these pages by hand; say
**"update docs"** to Claude to bring them up to date, and **"check module
docs"** to check the setup.

## How it stays current

- After each finished task that changed the project, Claude asks whether to
  document it, naming the module. A yes writes the history entry and
  refreshes the module's page.
- Work a session left undocumented is raised at the start of the next session
  on the same computer.

## Layout

| Path | What it is |
| --- | --- |
| `config.json` | The modules, the code each covers, excluded areas, publishing |
| `modules/<module>/overview.md` | The module's current state, rewritten on each update |
| `modules/<module>/history/<date>-<slug>.md` | One dated entry per piece of work |
| `engine/` | Generated by the skill - never edit it by hand |
| `local/` | This computer's own records and caches - gitignored |

## What never appears on a page

Hours, budgets or billing. People's names, emails or computers - the pages
never say who did what. Any mention of the tools used to build the work.
Internal requirement or decision IDs (requirements are named by their titles).
