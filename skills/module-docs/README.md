# Module Docs

This skill keeps one living page per product module for clients and developers: what it is, what's built, what's next, and a dated history of changes and decisions. It writes only after you say yes.

## When to Use This Skill

- A client wants to follow progress module by module, without reading commits
- A developer needs to know where a module lives and how it got there
- You want decisions and dropped options written down as the work happens
- An existing git history should become module pages once
- Earlier sessions finished work that nobody documented

## What This Skill Does

1. **Sets Up Once**: Installs its engine and two Claude Code hooks, asks how to publish
2. **Writes Every Module's Page**: Takes the module list from your product docs and confirms each module's code
3. **Rebuilds Past History**: Turns commits since a date you pick into dated entries
4. **Asks After Each Task**: Offers to document finished work under a module
5. **Catches Up**: Offers to document work earlier sessions left undocumented
6. **Publishes Only the Docs**: Commits and pushes only the docs, or leaves them to you

## How to Use

### Basic Usage

Install it into the project, then ask Claude from the project root:

```
aistack add module-docs
```

```
Set up module docs
```

Setup asks how the docs reach the repository and where the history should start, checks itself, and goes straight on to the first run.

### Document a Finished Task

Answer the question Claude asks after a task (Yes, under the module / Different module / Not now / Don't document), or say:

```
Document this
```

### Catch Up on Earlier Work

```
Update docs
```

### Add a Module or Leave an Area Out

```
Add a module
```

```
Exclude app/admin/
```

### Check the Setup

```
Check module docs
```

Run it after `aistack update` too: it compares the project with the installed skill and re-runs setup to fix what it can. `/module-docs` starts the skill directly.

## Example

After a task that added banner upload to the profile page, Claude asks:

```
Document this under Profiles? A banner can be uploaded to the profile page
  Yes, under Profiles / Different module / Not now / Don't document
```

**User**: Yes, under Profiles

**Result**: a new entry in `project-management/module-docs/modules/profiles/history/2026-10-17-banner-upload.md`:

```markdown
## What changed

A banner image can be uploaded to the profile page and is shown across the
full width on every screen size (`components/profile-header.tsx`).

## Why and the plan

This delivers the agreed banner upload.

## Decisions made

- The banner is cropped in the browser before upload, not on the server, so
  no uncropped image is ever stored.

## Open follow-ups

None.
```

The Profiles `overview.md` is rewritten to match, and in commit-and-push mode the docs go in as "Document Profiles: ..." and are pushed.

## Tips

- Have a modules list in your product docs first; the skill never invents modules
- Commit `.claude/settings.json`, `.gitignore` and `project-management/module-docs/` after setup
- "Not now" asks again next session; "Don't document" leaves the work out
- Pages never mention hours, people, AI tooling, internal IDs or commit SHAs
- It never pulls, rebases or forces; if the remote moved on, pull and push yourself
- Never hand-edit the engine or hooks; update the skill and run "check module docs"

## Related Use Cases

- `time-tracker` for hours and timesheets, which module pages deliberately leave out
- `project-kickoff`, which offers module-docs for new projects and leaves its setup as a next step
- Drawing the pages on the project's own site or as a PDF, following `references/page-format.md`

## Requirements

Node and git, with Claude Code for the hooks and the clickable questions.

## Files It Writes

| Path | What it is |
| --- | --- |
| `project-management/module-docs/config.json` | Modules, the code each covers, excluded areas, publishing |
| `project-management/module-docs/modules/<id>/overview.md` | The module now, rewritten on each update |
| `project-management/module-docs/modules/<id>/history/<YYYY-MM-DD>-<slug>.md` | One dated entry per piece of work |
| `project-management/module-docs/readme.md` | A short guide to the folder for readers |
| `project-management/module-docs/engine/` | Generated by setup; never edited by hand |
| `project-management/module-docs/local/` | This computer's records and caches, gitignored |
| `.claude/settings.json` | The SessionStart and Stop hooks |
